### Run order

This machine drifts thermally under sustained load, and an app measured 45 minutes into a saturated campaign is not being compared with one measured at minute two. The list is therefore swept more than once, in opposite directions, and every sweep's order is printed here so a reader can check any surprising result against where it sat in the queue.

1. pass 1: astro -> borgo -> elysia -> express -> fastify -> fresh -> hono -> nextjs
2. pass 2: nextjs -> hono -> fresh -> fastify -> express -> elysia -> borgo -> astro

## Configuration, as disclosed by each implementation

`bench.manifest.json` documents its `notes` field as "free text shown in the report". This is that. It is printed above the tables rather than below them because it is where an implementation admits to being started differently, tuned differently, or written without the fast mode its framework offers - and a caveat that only exists in a file nobody opens is not a caveat.

| app | started as | non-default environment | notes |
| --- | --- | --- | --- |
| astro | `node ./dist/server/entry.mjs` | none | Server output with the standalone Node adapter - self-hosted, like borgo. Every route sets `prerender = false`, because Astro's default would turn /page into a build-time static file and the scenario is per-request rendering. The React counter is an island (client:load), which is Astro's idiom; Astro therefore ships less client JS than the React frameworks here by design, not by accident. The shared dataset module is copied into src/lib at build time. |
| borgo | `bun node_modules/borgo-framework/src/cli.ts start` | `SESSION_SECRET=(redacted)`<br>`BUN_CONFIG_MAX_HTTP_REQUESTS=16384` | Two processes: the Bun front server on PORT and the Go API binary on API_PORT. /api/* is proxied by the front server, which is what a deployed borgo app does - so the JSON scenarios include the proxy hop. Measured against the borgo source in this repo (go.mod replace, package.json file: link), not a published release. BUN_CONFIG_MAX_HTTP_REQUESTS is raised from Bun's default of 256 because that default caps the number of concurrent requests the front server can have in flight to the Go API - which silently ceilings concurrent SSE streams at ~255. This is disclosed rather than quietly applied: see the finding in bench/README.md. Started via the CLI entrypoint directly, exactly as the shipped Dockerfile does, rather than through `bun run start`: the latter adds a shell and two launcher processes that RSS-of-the-tree would otherwise charge to borgo, and that no production deployment runs. |
| elysia | `bun server.js` | none | Bun-native router. Like Hono it does not claim the ssr-page scenario. Elysia's own benchmarks lean on compile-time schema specialisation that this plain implementation does not use, so treat these numbers as Elysia-as-written-here rather than Elysia-at-its-best. |
| express | `node server.js` | none | Run on Node, which is where Express lives; running it on Bun would be a different product. ETag generation is disabled because none of the other implementations hash their bodies - leaving it on would charge Express for a feature the comparison does not ask for. Does not claim ssr-page. |
| fastify | `node server.js` | none | Run on Node with the logger off. Fastify is fastest when given JSON response schemas so it can compile a serialiser; this implementation does not use them, because the contract's list is generated per request and the other implementations serialise generically. Fastify-with-schemas would be a fair separate entry, not a substitute for this one. Does not claim ssr-page. |
| hono | `bun server.js` | none | A router, not a meta-framework: it does not claim the ssr-page scenario, because rendering React through Hono would be an application we wrote rather than anything Hono provides. Included as a floor - it shows what the request plumbing costs when there is almost no framework above it. |
| nextjs | `node node_modules/next/dist/bin/next start --port ${PORT}` | none | Production build, self-hosted with `next start` on Node - the deployment borgo actually competes with, not Vercel's edge. Every route sets `dynamic = 'force-dynamic'`: left alone Next would prerender /page at build time and serve a static file, which is a different and much faster thing than server-rendering per request. Compression is off in next.config.mjs so every implementation ships identical bytes. The shared dataset module is copied into lib/ at build time because Next's bundler will not reach outside the project root. Started by invoking Next's own bin on node directly rather than through `bun x next start`: the runner charges RSS over the whole process tree, and `bun x` interposes a launcher that borgo - which is deliberately started without one, for exactly this reason - was not being charged for. Same rule for everyone or the memory table is not a comparison. |

> Tuning applied to **one** implementation and no other: `SESSION_SECRET=(redacted)` (borgo), `BUN_CONFIG_MAX_HTTP_REQUESTS=16384` (borgo). Each may be justified, and the notes above say why, but a knob given to one subject is a fact about the comparison and not an implementation detail.

## What this harness does not enforce

Everything above is checked in code. These are not, and no number here should be read as though they were:

- **That each competitor is implemented as well as its own experts would implement it.** The runner checks that a response satisfies CONTRACT.md; it cannot check that the code producing it is idiomatic or fast. Fastify's compiled response schemas and Elysia's schema specialisation are both deliberately unused here, and both would raise their numbers.
- **That the borgo implementation was not written with more care than the others.** It was written by the same people who wrote borgo. The harness has no way to measure that asymmetry.
- **That the load generator is not the bottleneck.** It runs on the same machine as the server under test, so at the top end these numbers compress toward each other and toward oha.
- **That the machine stayed quiet for the whole campaign.** The CPU is sampled before the first app and after the last one, and both readings are in the environment block above - but not continuously, and nothing stops a background update landing at minute twenty.
- **That latency percentiles mean what a service-level percentile means.** The load runs open-throttle, so they are saturation percentiles subject to coordinated omission.
